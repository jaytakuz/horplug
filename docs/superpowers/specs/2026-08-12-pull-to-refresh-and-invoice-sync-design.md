# Pull-to-Refresh, Invoice Sync & Typography — Design

## ปัญหา

การรีเฟรชข้อมูลในแอปทุกวันนี้ไม่มีมาตรฐานเดียวกัน และการแก้ยอดบิลที่ออกไปแล้วทำได้
ทางเดียวคือยกเลิกใบเดิมแล้วออกใบใหม่ ซึ่งกินเลขที่บิลและทิ้งการ์ดยอดผิดไว้ในแชทของผู้เช่า

- **หน้ามิเตอร์กับหน้าบิลฝั่งเจ้าของหอลากลงเพื่อรีเฟรชไม่ได้เลย** ทางเดียวที่จะเห็นข้อมูลใหม่
  คือสลับแท็บออกแล้วกลับเข้ามา ซึ่งไม่ได้โหลดใหม่ด้วยซ้ำเพราะ `IndexedStack` เก็บหน้าไว้ทั้งหมด
- **หน้าที่มี `RefreshIndicator` อยู่แล้วยังลบเนื้อหาทั้งหน้าทิ้งระหว่างรีเฟรช** เพราะ ViewModel
  มี `isLoading` ตัวเดียวแล้วหน้าจอแปลว่า "วาดตัวหมุนกลางจอ" — ตัวหมุนของ `RefreshIndicator`
  จึงหายไปกลางท่าทางที่ผู้ใช้ยังลากค้างอยู่ · `TenantBillsViewModel` แก้ปัญหานี้ไว้แล้วด้วย
  `_hasLoadedOnce` แต่แก้อยู่ตัวเดียวในสิบกว่าตัว
- **สถานะว่างและสถานะผิดพลาดเป็น `Center` เฉยๆ ซึ่งลากไม่ได้** หน้าที่โหลดล้มจึงกลายเป็นทางตัน
  ที่ไม่มีท่าทางไหนพาออกไปได้ นอกจากปุ่ม "ลองใหม่" ที่มีอยู่ในบางหน้าเท่านั้น
- **ยอดบิลไม่ตามความจริงของงวด** `invoices` ตรึงตัวเลข ณ วันออกตามที่
  [spec 2026-08-04](2026-08-04-invoice-generation-design.md) ตั้งใจไว้ เจ้าของหอที่จดเลขมิเตอร์
  ผิดหลักเดียว หรือกรอกค่าน้ำทีหลัง จึงต้อง void ใบเดิมแล้วออกใหม่เสมอ ทั้งที่ผู้เช่ายังไม่ได้จ่าย
- **ไม่มีท่าทางปัดขอบจอเพื่อย้อนกลับ** บน Android ได้อนิเมชันเริ่มต้นของ Flutter ที่ไม่ใช่
  ท่าทางพรีวิวตามมาตรฐาน Android 14+ ส่วนบนเว็บไม่มีท่าทางลากกลับเลย
- **ตัวอักษรไทยหน้าตาต่างกันทุกเครื่อง** เพราะแอปไม่ได้กำหนดฟอนต์ไว้ ตกไปใช้ของระบบ
  (Android=Noto, Windows=Tahoma, iOS=Thonburi) ซึ่งความสูงสระบน-ล่างไม่เท่ากันเลย

## เป้าหมาย

1. ทุกหน้าที่โหลดข้อมูลลากลงเพื่อรีเฟรชได้ โดย header และแถบนำทางไม่ขยับ และเนื้อหาเดิม
   ไม่หายระหว่างรีเฟรช
2. บิลที่ยังค้างชำระมียอดตรงกับข้อมูลล่าสุดของงวดเสมอ โดยไม่ต้องยกเลิกแล้วออกใหม่
3. ผู้เช่ารู้ทุกครั้งที่ยอดเปลี่ยน พร้อมเห็นว่าเปลี่ยนจากเท่าไรเป็นเท่าไร
4. ปัดจากขอบจอย้อนกลับได้ทั้ง Android, iOS และเว็บ พร้อมอนิเมชันตามมาตรฐานของแต่ละแพลตฟอร์ม
5. ตัวอักษรหน้าตาเดียวกันทุกเครื่องด้วย Open Sans คู่กับ Noto Sans Thai
6. ทุกหน้าแสดงผลได้พอดีตั้งแต่มือถือ 360dp ถึงเว็บ 1440px

## นอกขอบเขต

- แก้ยอดบิลที่ผู้เช่าส่งสลิปแล้ว จ่ายแล้ว หรือยกเลิกแล้ว — ตรึงตลอดไปเหมือนเดิม
- ให้ผู้เช่าแก้หรือคำนวณยอดเองได้ทุกรูปแบบ (RLS ให้สิทธิ์อ่านอย่างเดียว และยังคงเป็นแบบนั้น)
- realtime subscription — ยังใช้การดึงข้อมูลตามท่าทางของผู้ใช้เหมือนเดิม
- เปลี่ยนฟอนต์ของ PDF — ยังเป็น Sarabun ที่โหลดผ่าน `rootBundle` ตามเดิม
- ปัดซ้าย-ขวาเพื่อสลับแท็บ — ชนกับการเลื่อนแถวชิปตัวกรองและ TabBar ค่าไฟ/ค่าน้ำ
- แจ้งเตือน push เมื่อยอดบิลเปลี่ยน — ใช้ข้อความในแชทเป็นช่องทางเดียว

## การตัดสินใจที่กำหนดรูปร่างของงาน

| เรื่อง | เลือก | เหตุผล |
|---|---|---|
| สถานะโหลด | แยก `isLoading` (ครั้งแรก) ออกจาก `isRefreshing` | หน้าที่ลบเนื้อหาทิ้งตอนรีเฟรชทำให้ตัวหมุนของท่าทางหายกลางคัน และผู้ใช้เสียตำแหน่งที่เลื่อนค้างไว้ |
| ที่วาง `RefreshIndicator` | ในตัวหน้าจอ ไม่ใช่ครอบ `Scaffold` | header/bottom bar อยู่นอก `body` โดยโครงสร้างอยู่แล้ว การครอบทั้ง Scaffold จะลากทั้งแถบตามลงมา |
| สถานะว่าง/ผิดพลาด | เป็น scroll view ที่ลากได้เสมอ | `Center` ลากไม่ได้ หน้าที่โหลดล้มจึงไม่มีทางออกด้วยท่าทางเดียวกับที่ใช้ทั้งแอป |
| มิเตอร์ที่พิมพ์ค้างไว้ | ถามก่อนทิ้ง | `reloadTick` ล้าง `TextEditingController` ทุกครั้งที่โหลด การรีเฟรชเงียบๆ = เลขที่พิมพ์มาทั้งชั้นหายโดยไม่มีอะไรบอก |
| คำนวณยอดใหม่เมื่อไร | ตอนเขียน (ฝั่งเจ้าของหอ) | ผู้เช่าไม่มีสิทธิ์ UPDATE · และถ้าคำนวณสดตอนแสดง QR พร้อมเพย์กับแถวในฐานข้อมูลจะพูดคนละยอด |
| บิลที่ปรับได้ | `unpaid` เท่านั้น | ผู้เช่าที่ส่งสลิปแล้วจ่ายตามยอดที่เห็น การขยับยอดทีหลังทำให้สลิปกับบิลไม่ตรงกันโดยไม่มีใครผิด |
| ไม่มีเลขมิเตอร์ในงวด | ไม่แตะบิลใบนั้น | บิลที่ออกไปแล้วแปลว่าเคยมีเลข การที่มันหายคือข้อมูลถูกลบ ไม่ใช่ผู้เช่าใช้ไฟน้อยลง |
| เลขที่บิล/revision | คงเดิม | นี่คือใบเดิมที่ยอดถูกแก้ ไม่ใช่ใบแทน · การขยับ revision จะกินเลขที่บิลแบบเดียวกับ void + reissue ซึ่งเป็นสิ่งที่งานนี้มีไว้เพื่อเลี่ยง |
| ยอดรวม | ปล่อยให้ฐานข้อมูลคำนวณ | `total` เป็น `GENERATED ALWAYS AS` การเขียนแค่ส่วนประกอบจึงไม่มีทางทำให้ยอดรวมไม่ตรงกับผลบวก |
| ค่าห้องในการคำนวณใหม่ | ขยับตามราคาห้องปัจจุบัน | ผู้ใช้เลือกเอง หลังรับทราบผลข้างเคียงด้านล่าง |
| แจ้งผู้เช่า | ข้อความ `text` ในแชท + ป้ายบนการ์ด | การ์ดบิลเดิมในแชทแสดงยอดใหม่เองอยู่แล้ว (resolve ข้อมูลสด) แต่ผู้เช่าที่แคปหน้าจอ QR ไว้ต้องมีอะไรมาบอกว่าต้องสแกนใหม่ |
| ท่าทางย้อนกลับ | ตั้งที่ `pageTransitionsTheme` | ครอบทุกเส้นทางที่ push ในครั้งเดียว ไม่ต้องแก้หน้าจอสักหน้าและไม่มีหน้าไหนหลุด |
| ฟอนต์ | ฝังไฟล์ TTF มากับแอป | `google_fonts` โหลดตอนรัน = ครั้งแรกตัวหนังสือกระพริบเปลี่ยนฟอนต์ และเครื่องที่ไม่มีเน็ตไม่ได้ฟอนต์เลย |
| ฟอนต์ไทย | Noto Sans Thai | Open Sans ไม่มีอักษรไทยสักตัว · Noto Sans Thai ออกแบบให้เข้ากับโครงตัวอักษรตระกูลเดียวกัน จึงกลมกลืนเมื่ออยู่บรรทัดเดียวกัน |

## ผลข้างเคียงที่รับทราบและยอมรับแล้ว

**การขึ้นค่าเช่ามีผลย้อนหลังกับบิลที่ยังไม่จ่าย** — เมื่อการคำนวณใหม่รวมค่าห้องตามราคาปัจจุบัน
ของห้อง การแก้ราคาห้อง 101 จาก ฿3,000 เป็น ฿3,300 แล้วมีการยิงคำนวณใหม่ (บันทึกมิเตอร์
หรือรีเฟรชหน้าบิลของงวดนั้น) จะทำให้บิลค้างชำระของงวดเก่าขยับตามไปด้วย ทั้งที่ผู้เช่าได้รับบิล
ใบ ฿3,000 ไปแล้ว

สิ่งที่กันไม่ให้เรื่องนี้เกิดแบบเงียบๆ คือข้อความในแชทที่ระบุยอดเก่า→ยอดใหม่ทุกครั้งที่ยอดขยับ
และป้าย "ปรับยอดแล้ว" บนการ์ดบิล — ผู้เช่าจะเห็นเสมอว่าเกิดอะไรขึ้นและเมื่อไร

## 1 · โครงการรีเฟรชที่ใช้ร่วมกันทั้งแอป

### 1.1 กติกาสถานะโหลดสองชั้น

`lib/viewmodels/refreshable.dart` — mixin `RefreshableViewModel` บน `ChangeNotifier`:

| ฟิลด์ | ความหมาย | หน้าจอวาด |
|---|---|---|
| `isLoading` | โหลดครั้งแรก ยังไม่มีอะไรให้แสดง | ตัวหมุนกลางพื้นที่เนื้อหา (ใต้ header) |
| `isRefreshing` | มีข้อมูลอยู่แล้ว กำลังดึงใหม่ | คงเนื้อหาเดิมทั้งหมด ให้วงแหวนของ `RefreshIndicator` เป็นตัวบอกอย่างเดียว |

```dart
mixin RefreshableViewModel on ChangeNotifier {
  bool isLoading = true;
  bool isRefreshing = false;
  bool _hasLoadedOnce = false;
  bool get hasLoadedOnce => _hasLoadedOnce;

  /// ครอบงานโหลดหนึ่งครั้ง แล้วตั้งธงให้ถูกชั้นเอง
  ///
  /// ครั้งแรกตั้ง [isLoading] ครั้งถัดไปตั้ง [isRefreshing] · `finally` ปลดธง
  /// ทั้งสองเสมอ ความล้มจึงไม่ทำให้หน้าค้างอยู่กับตัวหมุนตลอดไป
  Future<void> runLoad(Future<void> Function() body);
}
```

ตัวที่ต้องย้ายมาใช้: `TenantBillsViewModel` (มีตรรกะนี้อยู่แล้วในชื่อ `_hasLoadedOnce`),
`TenantDashboardViewModel`, `TenantMaintenanceViewModel`, `TenantProfileViewModel`,
`DashboardViewModel`, `RoomsViewModel`, `MaintenanceOverviewViewModel`, `BillingViewModel`,
`MeterViewModel`

### 1.2 วิดเจ็ตกลาง

`lib/widgets/refreshable.dart`

- **`PullToRefresh`** — ห่อ `RefreshIndicator.adaptive` (iOS/macOS ได้ตัวหมุนแบบ Cupertino,
  Android/เว็บได้วงแหวน Material) ตั้งสี `AppColors.primary` บนพื้น `AppColors.card` ครั้งเดียว
  ให้ทั้งแอป · รับ `onRefresh` ที่คืน `Future<void>` ตามสัญญาเดิมของ Material
- **`CenteredScrollable`** — `CustomScrollView` + `SliverFillRemaining(hasScrollBody: false)` +
  `AlwaysScrollableScrollPhysics` สำหรับสถานะว่าง/ผิดพลาด ที่ต้องลากได้ทั้งที่เนื้อหาสั้นกว่าจอ

ทั้งสองตัวไม่รู้จัก ViewModel ตัวไหนเลย รับแค่ callback กับ child จึงทดสอบได้ด้วยข้อมูลปลอม

### 1.3 ทำไม header กับแถบนำทางนิ่งอยู่แล้ว

`AdaptiveNavigationScaffold` วาง `appBar` และ `bottomNavigationBar` เป็นพารามิเตอร์ของ
`Scaffold` ซึ่งอยู่คนละ subtree กับ `body` · `RefreshIndicator` ขยับได้เฉพาะลูกของมัน
ข้อกำหนด "header/bottom bar ต้องนิ่ง" จึงเป็นจริงโดยโครงสร้าง ตราบใดที่ไม่มีใครเอา
`RefreshIndicator` ไปครอบทั้ง `Scaffold` — เขียนไว้เป็นคอมเมนต์ในวิดเจ็ตกลางเพื่อกันคนแก้ทีหลัง

## 2 · หน้ามิเตอร์

### 2.1 ปัญหาที่ต้องแก้ก่อนแปะ RefreshIndicator

`_MeterViewState` สร้าง `TextEditingController` ต่อห้อง แล้วล้างทิ้งทั้งชุดเมื่อ
`viewModel.reloadTick` ขยับ · ถ้าปล่อยให้ท่าทางลากเรียก `loadAllRecords()` ตรงๆ
เลขมิเตอร์ที่เจ้าของหอพิมพ์ค้างไว้ทั้งชั้นจะหายทันทีโดยไม่มีอะไรเตือน

### 2.2 dirty tracking ที่บอกความจริง

`MeterViewModel` มี `modifiedWaterRoomIds` อยู่แล้ว แต่ฝั่งค่าไฟไม่มี และ `canSave` วันนี้
คืน `true` เพียงเพราะ "มีห้องไหนสักห้องที่มีเลขมิเตอร์" ซึ่งเป็นจริงเสมอหลังโหลดข้อมูลที่เคยบันทึกไว้

```dart
final Set<int> modifiedElectricityRoomIds = {};   // ใหม่

bool get hasUnsavedEdits =>
    modifiedElectricityRoomIds.isNotEmpty ||
    modifiedWaterRoomIds.isNotEmpty ||
    waterRecords.any((r) => r.id == null);

bool get canSave => !isLoading && !isSaving && hasUnsavedEdits;
```

`setElectricityReading` เพิ่ม `roomDbId` เข้าเซ็ต · `saveAll` ล้างทั้งสองเซ็ตเมื่อสำเร็จ ·
`saveAll` ยังส่ง `electricityRecords` ทั้งก้อนให้ service เหมือนเดิม (upsert ซ้ำได้ ไม่เสียหาย)
เซ็ตนี้มีไว้ตอบว่า "มีอะไรค้างอยู่ไหม" เท่านั้น

ผลพลอยได้: ปุ่ม "บันทึกทั้งหมด" หยุดกดได้ทั้งที่ไม่มีอะไรให้บันทึก

### 2.3 ท่าทางรีเฟรช

`PullToRefresh` ครอบแยกกันสองแท็บ (ค่าไฟ / ค่าน้ำ) ภายใน `TabBarView` · หัวหน้าจอ
ตัวเลือกงวด ช่องค้นหา และ `TabBar` อยู่นอก scroll view จึงนิ่งตลอด

เมื่อ `hasUnsavedEdits == true` การลากจะเปิดกล่องยืนยันก่อน:

> **มีเลขมิเตอร์ที่ยังไม่ได้บันทึก**
> รีเฟรชแล้วค่าที่พิมพ์ไว้จะหายทั้งหมด
> [ยกเลิก] [ทิ้งแล้วรีเฟรช]

กด "ยกเลิก" = คืน `Future` ทันที วงแหวนหดกลับเอง ไม่มีอะไรถูกโหลด

### 2.4 หลังบันทึกมิเตอร์

ลำดับใน `_handleSave` เปลี่ยนเป็น: บันทึกมิเตอร์ → **ปรับยอดบิลค้างชำระของงวดนั้น (§4)** →
snackbar สรุปผลทั้งสองอย่าง → กล่อง "ออกบิลใหม่" สำหรับห้องที่ยังไม่มีบิล

สองอย่างหลังไม่ทับกัน: การปรับยอดแก้ใบที่มีอยู่แล้ว ส่วนการออกบิลสร้างใบให้ห้องที่ยังไม่มี
(`previewDrafts` ข้ามห้องที่ออกบิลแล้วด้วย `SkipReason.alreadyIssued` อยู่แล้ว)

ถ้าการปรับยอดล้ม จะไม่ย้อนการบันทึกมิเตอร์ที่สำเร็จไปแล้ว แค่บอกใน snackbar — หลักเดียวกับที่
`postIssueNotices` ใช้: มิเตอร์คือของจริง การปรับบิลคือผลพวงของมัน

## 3 · หน้าบิล

### 3.1 ฝั่งเจ้าของหอ

`PullToRefresh` ครอบเฉพาะรายการบิล (ปุ่ม "ออกบิลใหม่" ตัวเลือกเดือน-ปี ลิงก์ตั้งค่าช่องทาง
รับเงิน และชิปตัวกรอง อยู่นอกกรอบ ไม่ขยับ) · สถานะว่างและสถานะผิดพลาดเปลี่ยนเป็น
`CenteredScrollable` เพื่อให้ลากได้เหมือนกัน

ท่าทางลากเรียก `BillingViewModel.refresh()` ซึ่ง **ยิงการคำนวณยอดใหม่ของงวดที่เลือกอยู่ก่อน
แล้วค่อยโหลดรายการ** ทำให้คำสัญญา "ลากแล้วยอดเปลี่ยน" เป็นจริงตรงๆ และครอบกรณีที่ค่าทำ
ความสะอาดเปลี่ยนจากหน้าอื่น

การเขียนจากท่าทางรีเฟรชเป็นเรื่องผิดปกติจึงต้องมีเงื่อนไขกำกับ: ทำเฉพาะฝั่งเจ้าของหอ (ผู้เช่า
ถูก RLS ปิดอยู่แล้ว) และเป็น no-op เมื่อไม่มีอะไรเปลี่ยน — ไม่มีการเขียน ไม่มีข้อความ

ถ้าการคำนวณล้มแต่การโหลดสำเร็จ: แสดงรายการตามปกติ + snackbar บอกว่าปรับยอดไม่สำเร็จ
(ที่นี่ใช้ snackbar ได้เพราะผู้ใช้เพิ่งทำท่าทางบนแท็บที่เห็นอยู่ ต่างจาก error ตอนโหลดอัตโนมัติ
ที่หน้านี้จงใจแสดงในตัวหน้าจอ เพราะ `IndexedStack` build ทุกแท็บพร้อมกันตั้งแต่เปิดแอป)

### 3.2 ฝั่งผู้เช่า

มี `RefreshIndicator` อยู่แล้วสามจุด เปลี่ยนมาใช้ `PullToRefresh` และตัด
`if (viewModel.isLoading) return Center(...)` ที่กินทั้งหน้าออก เหลือเฉพาะการโหลดครั้งแรก
ตามกติกา §1.1 · ท่าทางลากเป็นการอ่านอย่างเดียว ตัวเลขที่เห็นคือตัวเลขที่เจ้าของหอปรับไว้แล้ว

## 4 · คำนวณยอดบิลค้างชำระใหม่

### 4.1 ตรรกะเป็น Dart ล้วน

เพิ่มใน `lib/services/invoice_calculator.dart` (ไฟล์ที่ตั้งใจให้ไม่ import supabase หรือ flutter
เพื่อให้ทดสอบเรื่องเงินได้โดยไม่ต้องมีเครือข่าย):

```dart
/// สิ่งที่ต้องแก้ในบิลใบหนึ่ง เมื่อเทียบกับข้อมูลล่าสุดของงวด
class InvoiceAdjustment {
  final Invoice invoice;
  final double roomPrice;
  final double electricityUnits;
  final double electricityCost;
  final double waterCost;
  final double cleaningFee;
  final double previousTotal;
  final double newTotal;
}

/// null = ไม่ต้องแตะใบนี้
InvoiceAdjustment? revalueInvoice({
  required Invoice invoice,
  required Room room,
  MeterCharge? electricity,
  double? waterAmount,
  required double cleaningFee,
});
```

กฎครบชุด — แต่ละข้อมีเทสต์ของตัวเอง:

| # | กฎ | เหตุผล |
|---|---|---|
| 1 | `status != unpaid` → `null` | ใบที่ส่งสลิป/จ่าย/ยกเลิกแล้วตรึงตลอดไป |
| 2 | `electricity == null` → `null` | ไม่มีเลขมิเตอร์ในงวด = ข้อมูลถูกลบ ไม่ใช่ใช้ไฟน้อยลง · กันการลบพลาดกลายเป็นส่วนลดเงียบๆ |
| 3 | หน่วยไฟผ่าน `meterUnitsUsed` เสมอ | งวดที่มิเตอร์วน 9999→0000 ต้องได้หน่วยเท่ากับตอนออกบิล ไม่ใช่ติดลบ |
| 4 | `waterAmount == null` → คงค่าเดิมในบิล; มีค่า (รวม 0) → ใช้ค่านั้น | "ยังไม่กรอก" กับ "กรอกว่าไม่เก็บ" คนละความหมาย |
| 5 | ค่าทำความสะอาดใช้ค่าที่คำนวณได้ตรงๆ รวมทั้ง 0 | มาจากงานของงวดนั้น งานที่ถูกยกเลิกต้องหายจากบิลด้วย |
| 6 | ค่าห้องใช้ `room.price` ปัจจุบัน | ตามที่ผู้ใช้เลือก — ดู "ผลข้างเคียงที่รับทราบแล้ว" |
| 7 | ทุกค่าเท่าเดิม (ต่างน้อยกว่า 0.005) → `null` | กันข้อความสแปมในแชททุกครั้งที่กดบันทึก |

### 4.2 ฝั่งที่คุยกับฐานข้อมูล

`InvoiceService.syncUnpaidInvoices({dormitoryId, month, year}) → InvoiceSyncResult`

1. ดึงข้อมูลงวดชุดเดียวกับที่ `previewDrafts` ใช้ (ห้อง, `electricity_record`, `water_meter`,
   ค่าทำความสะอาด) — แยกออกมาเป็น `_fetchPeriodInputs()` ให้ทั้งสองเมธอดใช้ร่วมกัน
   แทนที่จะก๊อปคิวรีสี่ชุด
2. ดึงบิล `unpaid` ของงวดนั้น
3. เรียก `revalueInvoice` ทีละใบ เก็บเฉพาะใบที่คืนค่าไม่ใช่ `null`
4. `UPDATE` ทีละใบ พร้อมเงื่อนไขกันแข่ง:

```dart
await _client.from('invoices').update({
  'room_price': a.roomPrice,
  'electricity_units': a.electricityUnits,
  'electricity_cost': a.electricityCost,
  'water_cost': a.waterCost,
  'cleaning_fee': a.cleaningFee,
  'previous_total': a.previousTotal,
  'recalculated_at': DateTime.now().toUtc().toIso8601String(),
}).eq('id', a.invoice.dbId).eq('status', 'unpaid');
```

`total` ไม่อยู่ในชุดที่เขียน เพราะเป็น `GENERATED ALWAYS AS` ฐานข้อมูลคำนวณเอง

`.eq('status', 'unpaid')` ไม่ใช่ของประดับ: ถ้าผู้เช่ากดส่งสลิปในวินาทีเดียวกัน แถวจะเป็น
`pending` ไปแล้วและคำสั่งนี้จะไม่ match อะไรเลย — บิลที่มีสลิปแนบอยู่จึงไม่มีทางถูกขยับยอด
แม้ในภาวะแข่งกัน

### 4.3 ฐานข้อมูล

ไฟล์ใหม่ `database/invoices_recalculation.sql`:

```sql
ALTER TABLE invoices ADD COLUMN IF NOT EXISTS recalculated_at TIMESTAMPTZ;
ALTER TABLE invoices ADD COLUMN IF NOT EXISTS previous_total  NUMERIC;
```

พร้อมแก้คอมเมนต์ใน `invoices_schema.sql` ที่เขียนว่า "ตัวเลขที่ตรึงไว้ ณ วันออกบิล
ห้ามคำนวณใหม่จากมิเตอร์อีก" ซึ่งไม่จริงแล้วสำหรับใบที่ยังค้างชำระ — คอมเมนต์ที่โกหก
อันตรายกว่าไม่มีคอมเมนต์ · และเพิ่มไฟล์นี้เข้าลำดับการรันใน `database/README.md`

เพราะ `InvoiceService` เลือกด้วย `*` แอปจึงยังทำงานได้บนฐานข้อมูลที่ยังไม่ได้รันไฟล์นี้
(แค่ไม่มีป้าย "ปรับยอดแล้ว") แต่การปรับยอดจะล้มด้วย 42703 จนกว่าจะรัน ซึ่งเป็นความล้ม
ที่ไม่ทำลายอะไรตาม §2.4

`Invoice` รับสองฟิลด์ใหม่ (`recalculatedAt`, `previousTotal`) แบบ nullable และ
`_invoiceFromRow` อ่านแบบทนคอลัมน์ที่ยังไม่มี ตามแบบที่ `payment_method` ทำไว้

## 5 · แจ้งผู้เช่าเมื่อยอดเปลี่ยน

### 5.1 ข้อความในแชท

`InvoiceService.postAdjustmentNotices(List<InvoiceAdjustment>)` — insert ชุดเดียวเข้าตาราง
`messages` หนึ่งแถวต่อหนึ่งบิลที่เปลี่ยน:

> ยอดบิล INV-202608-101 งวดสิงหาคม 2026 เปลี่ยนจาก ฿3,200 เป็น ฿3,540 หลังปรับตามเลขมิเตอร์ล่าสุด

- `message_type: 'text'` ไม่ใช่ `'invoice'` — การ์ดบิลใบเดิมที่อยู่ในแชทแล้ว resolve ข้อมูลสด
  ผ่าน `invoicesByIdForRoom` จึงแสดงยอดใหม่เองอยู่แล้ว การส่งการ์ดซ้ำจะกลายเป็นการ์ดสองใบ
  ที่ยอดเท่ากันในห้องแชทเดียว
- ไม่ตั้ง `invoice_id` เพื่อไม่ให้ข้อความนี้ถูกตีความเป็นการ์ดโดยตัวเรนเดอร์ในอนาคต
- ระบุทั้งยอดเก่าและยอดใหม่ เพราะผู้เช่าที่แคปหน้าจอ QR ระบุยอดไว้ต้องรู้ว่าใบที่ถืออยู่ใช้ไม่ได้แล้ว
- ความล้มของขั้นนี้ไม่ย้อนการปรับยอด — บิลคือของจริง ข้อความคือการแจ้งเตือนเกี่ยวกับมัน
  (หลักเดียวกับ `postIssueNotices`)

### 5.2 ป้ายบนการ์ด

เมื่อ `invoice.recalculatedAt != null`:

- `TenantBillCard` และการ์ดบิลฝั่งเจ้าของหอขึ้นป้าย "ปรับยอดแล้ว" (`BadgeVariant.warning`)
- ใต้ยอดรวมมีบรรทัด "ยอดเดิม ฿3,200" เมื่อมี `previousTotal`
- `InvoiceDetailSheet` แสดงวันที่ปรับยอด

PDF และ QR พร้อมเพย์สร้างจาก `invoice.total` สดอยู่แล้ว จึงถูกต้องเองโดยไม่ต้องแก้

## 6 · ท่าทางย้อนกลับและอนิเมชันเปลี่ยนหน้า

ตั้งที่ `buildAppTheme()` จุดเดียว:

```dart
pageTransitionsTheme: PageTransitionsTheme(builders: {
  TargetPlatform.android: kIsWeb
      ? const CupertinoPageTransitionsBuilder()
      : const PredictiveBackPageTransitionsBuilder(),
  TargetPlatform.iOS:     const CupertinoPageTransitionsBuilder(),
  TargetPlatform.macOS:   const CupertinoPageTransitionsBuilder(),
  TargetPlatform.windows: const CupertinoPageTransitionsBuilder(),
  TargetPlatform.linux:   const CupertinoPageTransitionsBuilder(),
}),
```

- **Android (แอป)** — `PredictiveBackPageTransitionsBuilder` + เพิ่ม
  `android:enableOnBackInvokedCallback="true"` ที่ `<application>` ใน `AndroidManifest.xml`
  ได้ท่าทางปัดขอบพร้อมพรีวิวหน้าถัดไปตามมาตรฐาน Android 14+
- **เว็บทุกแพลตฟอร์ม + iOS/macOS/เดสก์ท็อป** — `CupertinoPageTransitionsBuilder` ซึ่งมี
  `CupertinoBackGestureDetector` มาในตัว = ลากจากขอบซ้ายกลับได้ทั้งด้วยนิ้วและด้วยเมาส์
  · ต้องแยกด้วย `kIsWeb` เพราะ predictive back อาศัย platform channel ของ Android
  ซึ่งไม่มีบนเบราว์เซอร์ แล้วจะตกกลับไปเป็น zoom transition ที่ไม่มีท่าทางลากเลย

หน้าที่ย้อนกลับไปคงสภาพเดิมอยู่แล้ว เพราะแท็บหลักอยู่ใน `IndexedStack` ไม่ถูกสร้างใหม่
และเมื่อกลับจากแผ่นซ้อนที่แก้ข้อมูล การโหลดซ้ำจะเข้าเส้น `isRefreshing` ตาม §1.1
— เห็นเนื้อหาเดิมระหว่างดึงข้อมูล แทนหน้าขาวที่มีตัวหมุน

ปุ่ม back ของเบราว์เซอร์ยังทำงานผ่าน go_router ตามเดิม ไม่ถูกแตะ

## 7 · ฟอนต์

### 7.1 ไฟล์และการประกาศ

ดาวน์โหลด TTF แบบ static ลง `lib/assets/fonts/`:

| ตระกูล | น้ำหนัก |
|---|---|
| Open Sans | 400, 600, 700 |
| Noto Sans Thai | 400, 600, 700 |

ประกาศใต้ `fonts:` ใน `pubspec.yaml` — คนละที่กับ Sarabun ซึ่งประกาศเป็น `assets:`
เพราะแพ็กเกจ pdf โหลดเองผ่าน `rootBundle` · ไม่แตะการประกาศเดิม

ถ้าไฟล์รวมทั้งหกเกิน 1MB ให้ตัดน้ำหนัก 600 ออกทั้งสองตระกูล เหลือ 400/700
(Flutter เลือกน้ำหนักใกล้เคียงให้เองเมื่อไม่มีตัวที่ขอ) — Open Sans พก greek/cyrillic/hebrew
มาด้วยจึงหนักกว่าที่คาด และงานนี้ไม่มี pipeline สำหรับ subset ฟอนต์

### 7.2 การต่อเข้าธีม

```dart
ThemeData(
  fontFamily: 'Open Sans',
  fontFamilyFallback: const ['Noto Sans Thai'],
  ...
)
```

ตัวอักษรที่ Open Sans ไม่มี (ภาษาไทยทั้งหมด) ตกไป Noto Sans Thai ทีละตัวอักษรโดยอัตโนมัติ
· `Text` ที่ใส่ `TextStyle` แบบ hardcode ไว้ทั่วแอปได้ฟอนต์ตามไปด้วย เพราะสไตล์เหล่านั้น
merge ทับ `DefaultTextStyle` ไม่ได้แทนที่ทั้งก้อน

`_buildTextTheme` ต้องไม่ถูกเขียนใหม่เป็น `const TextStyle` ก้อนใหม่ — คอมเมนต์ที่มีอยู่แล้ว
ใน `app_theme.dart` อธิบายเหตุผลไว้ครบ (จะทิ้ง `fontFamily`/`height`/`letterSpacing` ไป
แล้ว slot ที่แก้กับไม่ได้แก้จะใช้ฟอนต์คนละตัว ซึ่งเห็นชัดในภาษาไทยเพราะระยะสระไม่เท่ากัน)
งานนี้ยิ่งทำให้คอมเมนต์นั้นเป็นจริงกว่าเดิม

### 7.3 เว็บ

- `<link rel="preload" as="font" type="font/ttf" crossorigin>` ให้ `OpenSans-Regular.ttf`
  กับ `NotoSansThai-Regular.ttf` ใน `web/index.html` ลดจังหวะที่ตัวหนังสือกระพริบเปลี่ยนฟอนต์
- เปลี่ยน `font-family` ของ `#loading` ให้เข้าชุดกับแอปแทน `system-ui` ปัจจุบัน

### 7.4 ใบอนุญาต

ทั้งสองตระกูลเป็น SIL OFL 1.1 — เก็บไฟล์ `OFL.txt` ไว้ข้างฟอนต์และลงทะเบียนผ่าน
`LicenseRegistry.addLicense` ใน `main()` เพื่อให้ปรากฏในหน้า licenses ของแอปตามที่ควรเป็น

## 8 · การแสดงผลข้ามอุปกรณ์

ตรวจสามความกว้างตาม `Breakpoints` ที่โปรเจกต์นิยามไว้แล้ว:

| ขนาด | ความกว้าง | ตัวแทน |
|---|---|---|
| compact | 360×740 | มือถือแคบสุดที่ต้องรองรับ |
| medium | 800×1280 | แท็บเล็ต / หน้าต่างครึ่งจอ |
| expanded | 1440×900 | เว็บบนเดสก์ท็อป |

จุดที่รู้ล่วงหน้าว่าเสี่ยงและต้องแก้:

- หัวหน้ามิเตอร์กับหัวหน้าบิล — `Row` ที่มีคอลัมน์ข้อความคู่กับ `PrimaryButton` ความกว้าง
  ตามเนื้อหา ("กำลังบันทึก..." ยาวกว่า "บันทึกทั้งหมด") ล้นที่ 360dp
- การ์ดมิเตอร์ค่าไฟ — ชื่อผู้เช่า/หน่วย/ราคา/ไอคอนอยู่แถวเดียวกันหมด
- การ์ดบิลทั้งสองฝั่ง — ป้าย "ปรับยอดแล้ว" ที่เพิ่มเข้าไปใน §5.2 ไปเบียดแถวที่แน่นอยู่แล้ว

`test/responsive_widget_test.dart` pump วิดเจ็ตสาธารณะ (`TenantBillCard`, `MobileHeader`,
`StatCard`, `AdaptiveNavigationScaffold`) ทั้งสามขนาดแล้ว fail เมื่อ `tester.takeException()`
คืน overflow · หน้าจอเต็มสร้าง ViewModel ที่ต่อ Supabase ตั้งแต่ constructor จึง pump ไม่ได้
ตรวจด้วยการรันจริงบน Chrome แล้วปรับขนาดหน้าต่างแทน
