# Auto-issued Invoices & Landlord Shortcuts — Design

## ปัญหา

ระบบบิลใน [`docs/superpowers/specs/2026-08-04-invoice-generation-design.md`](2026-08-04-invoice-generation-design.md)
ทำงานครบวงแล้ว — ตาราง `invoices` ตรึงตัวเลข ณ วันออก มีวงจรชำระเงิน มีการ์ดบิลในแชท
มี QR พร้อมเพย์ระบุยอด แต่ทั้งหมดยัง**รอให้เจ้าของหอเดินไปกดเอง**และกระจายอยู่คนละที่

- **การออกบิลไม่ผูกกับเหตุการณ์ที่ทำให้ออกบิลได้** เจ้าของหอจดมิเตอร์เสร็จที่หน้ามิเตอร์
  แล้วต้องจำเองว่าต้องเดินไปหน้าบิลอีกหน้าเพื่อกดออก · กล่องที่เด้งหลังบันทึกทุกวันนี้
  ถามแค่ว่า "จะไปหน้าจัดการบิลไหม" ซึ่งเป็นการชี้ทาง ไม่ใช่การทำงานให้จบ
- **กฎ "ครบข้อมูล" หลวมกว่าที่ตั้งใจ** `buildDraft` ข้ามห้องก็ต่อเมื่อขาด**ครบทั้งสาม**
  อย่าง (ไฟ น้ำ ค่าทำความสะอาด) ห้องที่มีงานทำความสะอาดในงวดนั้นจึงได้บิลที่มีค่าไฟ ฿0
  ทั้งที่ยังไม่มีใครอ่านมิเตอร์เลย ผู้เช่าได้ QR ระบุยอดที่ยอดผิด
- **ผู้เช่าที่ได้การ์ดบิลในแชทยังต้องเปิดหน้าบิลก่อนถึงจะจ่ายได้** ทั้งที่ payload
  พร้อมเพย์ของบิลใบนั้นสร้างได้ตั้งแต่ในการ์ด
- **เจ้าของหอทวงบิลซ้ำในแชทไม่ได้** `postIssueNotices` ข้ามใบที่เคยแจ้งแล้วโดยตั้งใจ
  ซึ่งถูกสำหรับปุ่ม "ส่งอีกครั้ง" ตอนออกบิลล้ม แต่แปลว่าไม่มีทางส่งการ์ดใบเดิมซ้ำเลย
- **ทางลัดบนแดชบอร์ดเจ้าของหอ hardcode ไว้สี่ปุ่ม** ต่างจากฝั่งผู้เช่าที่จัดเองได้
  และ badge บนปุ่ม "สร้างบิล" เป็นเลข `'5'` ที่เขียนตายตัวไว้ในโค้ด ไม่ได้มาจากข้อมูลใด
- **ประวัติการแจ้งซ่อมดูได้ทีละห้องเท่านั้น** ทางเข้าเดียวคือหน้าห้องพัก → เลือกห้อง
  เจ้าของหอที่อยากรู้ว่า "ตอนนี้มีห้องไหนแจ้งอะไรเข้ามาบ้าง" ต้องไล่เปิดทีละห้อง

## เป้าหมาย

1. จดมิเตอร์เสร็จ = ออกบิลได้ทันทีในที่เดียว โดยยังเห็นว่าจะออกให้ห้องไหนก่อนยืนยัน
2. ไม่มีเลขมิเตอร์ไฟ = ไม่มีบิล = ไม่มี QR ระบุยอด
3. ผู้เช่าสแกนจ่ายได้จากการ์ดในแชทโดยไม่ต้องเปิดหน้าอื่น
4. เจ้าของหอจัดทางลัดบนแดชบอร์ดเองได้แบบเดียวกับผู้เช่า
5. มีหน้ารวมประวัติแจ้งซ่อม/ทำความสะอาดทั้งหอ เรียงตามคำขอล่าสุด

## นอกขอบเขต

- ออกบิลอัตโนมัติแบบไม่ถามยืนยัน — ดูเหตุผลใน "การตัดสินใจ" ด้านล่าง
- ตั้งเวลาออกบิลอัตโนมัติรายเดือน (cron / Edge Function)
- แจ้งเตือน push เมื่อบิลออก — ยังใช้การ์ดในแชทเป็นช่องทางเดียวเหมือนเดิม
- เปลี่ยนแปลงฐานข้อมูล — งานทั้งชุดนี้ไม่มี migration ใหม่สักไฟล์
- ทางเข้าหน้ารวมประวัติแจ้งซ่อมจาก bottom navigation

## การตัดสินใจที่กำหนดรูปร่างของงาน

| เรื่อง | เลือก | เหตุผล |
|---|---|---|
| Trigger การออกบิล | บันทึกมิเตอร์แล้วเด้งกล่องยืนยัน | บิลคือหลักฐานการเงิน พิมพ์เลขมิเตอร์ผิดหลักเดียวแล้วออกทันทีหมายถึงต้อง void + reissue ซึ่งกินเลขที่บิลและผู้เช่าเห็นการ์ดที่ผิดในแชทไปแล้ว |
| เปิดกล่องเมื่อไร | โหลด preview ก่อน ไม่มีห้องให้ออกก็ไม่เปิด | ไม่งั้นคนที่แก้ค่าน้ำของงวดที่ออกบิลครบแล้วจะโดนกล่องเปล่าเด้งใส่ทุกครั้งที่กดบันทึก |
| กล่องที่หน้าบิล | ยังเปิดเสมอแม้ไม่มีห้องให้ออก | ที่นั่นเจ้าของหอตั้งใจกด คำตอบว่า "ไม่มีห้องที่ออกบิลได้" คือสิ่งที่เขามาหา |
| เกณฑ์ครบข้อมูล | เลขมิเตอร์ไฟเป็นเงื่อนไขบังคับ | ค่าไฟเป็นก้อนที่ผันแปรที่สุดในบิล บิลที่ออกโดยไม่มีมันคือบิลที่ยอดผิดแน่ๆ ส่วนค่าน้ำที่ยังไม่กรอกคิดเป็น 0 ตามเดิม |
| QR ในการ์ดแชท | เฉพาะบิล `unpaid` และเฉพาะฝั่งผู้เช่า | บิลที่ส่งสลิปแล้ว/จ่ายแล้ว/ยกเลิกแล้วยังโชว์ QR คือการเชิญให้จ่ายซ้ำ · เจ้าของหอสแกน QR ของตัวเองไม่มีความหมาย |
| ส่งการ์ดซ้ำ | เมธอดใหม่ ไม่แก้ `postIssueNotices` | สองปุ่มมีเจตนาคนละอย่าง — "แจ้งให้ครบ" (ต้องกันซ้ำ) กับ "แจ้งอีกที" (ต้องซ้ำได้) การรวมเป็นตัวเดียวทำให้ตัวใดตัวหนึ่งพัง |
| โครงทางลัดสองฝั่ง | ทำของเดิมให้ generic | คัดลอก `QuickActionStore`/`ViewModel`/editor ไปอีกชุดแปลว่าบั๊กที่แก้ฝั่งหนึ่งต้องจำไปแก้อีกฝั่งตลอดไป |
| คีย์ที่เก็บทางลัด | ผู้เช่าคงคีย์เดิมเป๊ะ | `quick_actions.$userId` ถูกใช้อยู่บนเครื่องจริง เปลี่ยนคีย์ = ทุกคนเสียการจัดปุ่มที่ทำไว้โดยไม่มีอะไรบอก |
| หนึ่งแถวในหน้ารวมประวัติ | หนึ่งห้อง | เจ้าของหอคิดเป็นห้อง ไม่ใช่เป็นคำขอ · และ feed รวมทำให้ห้องที่แจ้งบ่อยกลบห้องอื่นจนหมด |
| หน้ารายห้อง | ใช้ `MaintenanceHistoryScreen` เดิม | มีครบทั้งค้นหา กรองสถานะ แก้ค่าทำความสะอาด อยู่แล้ว ต่างกันแค่ทางเข้า |

## 1 · Trigger ออกบิลจากการบันทึกมิเตอร์

### กฎ "ครบข้อมูล"

`buildDraft` ใน `lib/services/invoice_calculator.dart` ลำดับการตัดสินเดิมคือ
ไม่มีผู้เช่า → ออกบิลไปแล้ว → ไม่มีข้อมูลคิดเงิน โดยข้อสุดท้ายเขียนว่า

```dart
} else if (electricity == null && waterAmount == null && cleaningFee <= 0) {
```

เปลี่ยนเป็น `} else if (electricity == null) {` ลำดับสามข้อคงเดิม ไม่แตะอะไรอื่น
ป้ายของ `SkipReason.noMeterReading` เปลี่ยนเป็น "ยังไม่จดมิเตอร์ไฟ" ให้ตรงกับกฎใหม่

ผลฝั่งผู้เช่าได้มาฟรีจากโครงสร้างที่มีอยู่ — ไม่มีแถวใน `invoices` แปลว่า
`fetchCurrentForRoom` คืน `null` การ์ดบิลไม่ขึ้น ปุ่มชำระไม่มี และ `PaymentSheet`
ซึ่งเป็นที่เดียวที่วาด QR ระบุยอดเปิดจากบิลเท่านั้น **ไม่ต้องแก้โค้ดฝั่งผู้เช่าเลย**

### ตัว Trigger

`_handleSave` ใน `lib/screens/admin/meter_screen.dart` ตอนนี้เรียก `_showSuccessDialog`
ที่ถามว่าจะไปหน้าจัดการบิลไหม เปลี่ยนเป็นเรียกกล่องออกบิลของงวดที่กำลังกรอกอยู่
(`viewModel.selectedMonth` / `selectedYear`) แทน

เพิ่ม `maybeShowIssueInvoicesDialog()` ใน `lib/widgets/issue_invoices_dialog.dart`

```
สร้าง InvoiceIssueViewModel → await load() → drafts ว่าง? → จบเงียบๆ
                                           → ไม่ว่าง?   → showDialog ด้วย .value
```

ต่างจาก `showIssueInvoicesDialog` เดิมที่สร้าง ViewModel ใน `builder` แล้วให้กล่อง
โหลดเอง — ที่นั่นกล่องเปิดก่อนรู้ผล ซึ่งเหมาะกับหน้าบิลแต่ไม่เหมาะกับ trigger อัตโนมัติ
ทั้งสองทางใช้ ViewModel ตัวเดียวกัน ตรรกะการออกบิลจึงไม่ได้ถูกเขียนซ้ำ

**ขอบเขตของบิลที่ออก** เป็นทั้งหอเหมือนเดิม ไม่ใช่เฉพาะห้องที่เพิ่งกรอกในรอบนั้น
เพราะห้องที่กรอกไว้เมื่อวานแล้วยังไม่ได้ออกบิลก็ควรได้ออกพร้อมกัน และกล่องแสดงรายชื่อ
ห้องทั้งหมดที่จะออกก่อนยืนยันอยู่แล้ว จึงไม่มีอะไรเกิดขึ้นแบบที่มองไม่เห็น

## 2 · Invoice แบบ Dynamic ในแชท

### QR ระบุยอดในการ์ด

`InvoiceChatCard` รับพารามิเตอร์ใหม่ `promptPayId` (nullable) แล้ววาด `PromptPayQr`
ใต้ยอดรวมเมื่อครบสามข้อ — เป็นฝั่งผู้เช่า · บิล `unpaid` · สร้าง payload ได้

payload มาจาก `promptPayPayload()` ตัวเดียวกับที่ `PaymentSheet` และ `invoice_pdf`
เรียก QR ในแชท ในแผ่นชำระเงิน และใน PDF จึงเป็นอันเดียวกันเสมอ

ฝั่งผู้เช่า `TenantChatViewModel` มี `paymentChannel` อยู่แล้วผ่าน mixin
`TenantSlipSubmission` จึงเป็นการส่งต่อค่าที่โหลดมาแล้ว ไม่ใช่ query เพิ่ม
ฝั่งเจ้าของหอส่ง `null` ลงไป การ์ดก็เป็นการ์ดปกติเหมือนเดิม

### ปุ่มส่งบิลเข้าแชทด้วยมือ

`InvoiceService.sendInvoiceCard(invoice)` — insert ข้อความ `message_type = invoice`
ตรงๆ ไม่เช็คว่าเคยส่งแล้วหรือยัง ต่างจาก `postIssueNotices` ที่ต้องกันซ้ำเพราะมันคือ
การแจ้งรอบแรกของบิลทั้งชุด

ปุ่ม "ส่งบิลเข้าแชท" อยู่ใน `InvoiceDetailSheet` ฝั่งเจ้าของหอ ข้างปุ่มยกเลิกบิล
แสดงเมื่อบิลเป็น `unpaid` หรือ `pending` เท่านั้น — บิลที่จ่ายแล้วไม่มีอะไรให้ทวง
และบิลที่ยกเลิกแล้วการส่งการ์ดซ้ำคือการส่งใบที่ตายแล้วไปให้ผู้เช่าอ่าน

## 3 · ทางลัดปรับแต่งได้ฝั่ง Landlord

### ทำของเดิมให้ใช้ได้สองฝั่ง

```dart
abstract interface class QuickActionSpec {
  String get name;         // enum ให้มาเองอยู่แล้ว — ใช้เป็นค่าที่เขียนลงดิสก์
  String get label;
  String get description;
}
```

`QuickAction` (ผู้เช่า) implement มัน และเพิ่ม `LandlordQuickAction` อีกตัว
ส่วน `QuickActionStore` · `QuickActionsViewModel` · `showQuickActionsEditor`
กลายเป็น generic บน `T extends QuickActionSpec` โดยรับ `keyPrefix`, `values`,
`defaults` เข้ามาแทนการอ้าง `QuickAction` ตรงๆ

พฤติกรรมฝั่งผู้เช่าต้องไม่เปลี่ยนแม้แต่นิดเดียว รวมถึงความต่างระหว่าง
"ไม่เคยบันทึก" (คืนค่าตั้งต้น) กับ "บันทึกเป็นรายการว่าง" (ตั้งใจลบจนหมด)
และคีย์ `quick_actions.$userId` · ฝั่งเจ้าของหอใช้ `landlord_quick_actions.$userId`

ไอคอนกับสีอยู่ในไฟล์หน้าจอเหมือนที่ฝั่งผู้เช่าทำ ไม่ย้ายเข้า `models/`
เพราะไฟล์ใน `models/` ไม่ import material และไม่ควรเริ่มตอนนี้

### รายการทางลัด

| ทางลัด | ปลายทาง | badge |
|---|---|---|
| บันทึกมิเตอร์ | `/landlord/meter` | — |
| ออกบิล | `/landlord/billing` | — |
| จัดการห้อง | `/landlord/rooms` | — |
| สัญญาเช่า | `/landlord/lease` | — |
| แชท | `/landlord/chat` | ข้อความที่ยังไม่อ่าน |
| ประวัติแจ้งซ่อม | `/landlord/maintenance` | — |
| บิลรอตรวจสลิป | `/landlord/billing` | บิลที่ `status = pending` |
| ตั้งค่าช่องทางชำระเงิน | หน้า `PaymentChannelScreen` | — |

ค่าเริ่มต้น: **บันทึกมิเตอร์ · ออกบิล · สัญญาเช่า · แชท** — สี่ปุ่มเดียวกับที่อยู่บน
หน้าจอวันนี้เป๊ะ เจ้าของหอที่ใช้อยู่จึงไม่ตื่นมาเจอปุ่มย้ายที่โดยไม่ได้สั่ง

badge เลข `'5'` ที่ hardcode ไว้บนปุ่มสร้างบิลถูกลบทิ้ง แทนที่ด้วย
`InvoiceService.countAwaitingReview(dormitoryId)` บนทางลัด "บิลรอตรวจสลิป"
ซึ่งเป็นจำนวนจริงจากฐานข้อมูล

## 4 · หน้ารวมประวัติแจ้งซ่อม/ทำความสะอาด

### ข้อมูล

`RoomMaintenanceSummary` — ห้อง, ชั้น, ชื่อผู้เช่า, คำขอล่าสุด (ชนิด/ข้อความ/สถานะ/เวลา),
จำนวนงานที่ยังไม่เสร็จ, จำนวนทั้งหมด

`SupabaseService.fetchMaintenanceSummaries({required int dormitoryId})` ยิง query เดียว
join `rooms!inner(room_number, floor, dorm_id)` กรองด้วย `rooms.dorm_id` เรียง
`requested_at` จากใหม่ไปเก่า แล้วจัดกลุ่มต่อห้องใน Dart — แถวแรกของแต่ละห้องคือคำขอล่าสุด
โดยไม่ต้องเขียน SQL `DISTINCT ON` หรือสร้าง view ใหม่

ไม่ใส่ `limit` เพราะหอขนาดนี้มีคำขอนับได้ด้วยหลักร้อย และ `limit` ที่ตัดตรงกลางจะทำให้
ห้องที่แจ้งครั้งสุดท้ายนานแล้ว**หายไปจากรายการทั้งห้อง** ไม่ใช่แค่แสดงข้อมูลเก่า

### หน้าจอ

`MaintenanceOverviewScreen` ยืมโครงหน้ารวมแชทมาทั้งชุด — ช่องค้นหา (เลขห้อง/ชื่อผู้เช่า)
→ ชิปกรองชั้น → `PaperCard` ต่อห้อง แสดงเลขห้อง+ชื่อผู้เช่า / ข้อความคำขอล่าสุดบรรทัดเดียว /
เวลาแบบ "3 ชม.ที่แล้ว" พร้อม badge จำนวนงานค้าง เรียงตามเวลาคำขอล่าสุด

แตะแล้ว `Navigator.push` เข้า `MaintenanceHistoryScreen(roomId, roomNumber)` ที่มีอยู่แล้ว

`_formatMessageTime` ที่ตอนนี้เป็น private อยู่ใน `chat_screen.dart` ย้ายขึ้นเป็น
`formatRelativeTime` ใน `lib/utils/formatters.dart` แล้วใช้ร่วมกัน — สองรายการที่หน้าตา
เหมือนกันแต่ถือนาฬิกาคนละเรือนคือจุดที่ค่อยๆ เพี้ยนออกจากกันโดยไม่มีใครสังเกต

route `/landlord/maintenance` เป็นหน้าที่เจ็ดใน `AdminShell`
`_calculateSelectedIndex` คืน 6 ส่วน `bottomNavIndex` ที่เขียนไว้ว่า
`activeIndex <= 4 ? activeIndex : 0` รองรับอยู่แล้ว (หน้าสัญญาเช่าเดินทางนี้อยู่)
bottom navigation จึงยังมีห้าแท็บเท่าเดิม ไม่มีแถบไหนแคบลง
