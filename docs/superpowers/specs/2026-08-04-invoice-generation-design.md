# Invoice Generation — Design

วันที่ 4 สิงหาคม 2026 · สาขา `feature-invoice-generation`

## ปัญหา

บิลในแอปตอนนี้ไม่มีตัวตน `SupabaseService.fetchInvoices` ประกอบมันขึ้นใหม่ทุกครั้งที่เปิดหน้า
จาก `rooms.base_price` + `electricity_record` + `water_meter` + `maintenance_requests.cleaning_fee`
ผลคือ

- **บิลไม่ถูกตรึง** เจ้าของหอแก้ค่าห้องหรือแก้มิเตอร์ย้อนหลังเมื่อไร บิลเดือนที่แล้วที่ผู้เช่าจ่ายไปแล้ว
  เปลี่ยนตัวเลขตามทันที ไม่มีหลักฐานว่าตกลงกันที่ยอดเท่าไร
- **ไม่มีวงจรชำระเงิน** `status` ฝั่งเจ้าของหอ hardcode เป็น `unpaid` เสมอ ส่วนฝั่งผู้เช่าใช้
  `MockPaymentLedger` ที่เก็บสถานะไว้ใน memory และหายเมื่อปิดแอป
- **ปุ่ม "ออกบิลใหม่" ไม่ได้ออกบิล** มันเรียก `loadInvoices()` ซ้ำเท่านั้น
- **เจ้าของหอไม่มีที่ตรวจสลิป** ปุ่ม "ดูสลิป" มี `onPressed: () {}` ว่างเปล่า
- **ผู้เช่าไม่รู้ว่าบิลออกแล้ว** ต้องเปิดแอปมาเช็คเอง ต่างจากคำขอซ่อมที่โพสต์เข้าแชทให้อัตโนมัติ

## เป้าหมาย

1. บิลที่ออกแล้วเป็นแถวจริงในฐานข้อมูล ตัวเลขตรึง ณ วันออก
2. วงจรชำระเงินครบวง — ออกบิล → อัปสลิป → เจ้าของหออนุมัติหรือปฏิเสธ → ชำระแล้ว
3. ออกบิลแล้วโพสต์การ์ดบิลเข้าห้องแชทอัตโนมัติ
4. Export บิลเป็น PDF ภาษาไทยได้ทั้งสองฝั่ง

## นอกขอบเขต

- Dynamic PromptPay QR ที่ฝังจำนวนเงิน — เฟสนี้ใช้ภาพนิ่ง `lib/assets/sample_paymant_qrcode.jpg`
  คู่กับเลขบัญชีธนาคารกสิกรไทย 1438323216
- ตั้งค่ากำหนดชำระต่อหอ — ตรึงไว้ที่วันที่ 5 ของเดือนถัดไป
- ค่าบริการชนิดอื่นนอกจากค่าห้อง ค่าไฟ ค่าน้ำ ค่าทำความสะอาด
- ชำระเงินอัตโนมัติ ตรวจสลิปอัตโนมัติ ทวงหนี้อัตโนมัติ
- เก็บไฟล์ PDF ไว้บนเซิร์ฟเวอร์

## การตัดสินใจที่กำหนดรูปร่างของงาน

| เรื่อง | เลือก | เหตุผล |
|---|---|---|
| รูปร่างการเก็บ | ตารางเดียว คอลัมน์ตายตัว | ค่าใช้จ่ายของหอนี้นิ่งแล้ว 4 ชนิด การเพิ่มตาราง `invoice_items` ตอนนี้จะได้ผลลัพธ์เท่ากันเป๊ะแต่ต้องเขียนชั้นพับรายการเพิ่ม |
| การออกบิล | ออกทั้งหอ ข้ามห้องที่ไม่พร้อม | หอ 30 ห้องไม่ควรต้องกด 30 ครั้ง และห้องที่ยังไม่จดมิเตอร์ไม่ควรบล็อกทั้งหอ |
| แก้บิลที่ออกไปแล้ว | ยกเลิกแล้วออกใหม่ | บิลคือหลักฐานการเงิน การแก้ทับทำให้ตรวจย้อนหลังไม่ได้ว่าตัวเลขเคยเป็นเท่าไร |
| ปฏิเสธสลิป | กลับเป็น `unpaid` + เหตุผล | สิ่งที่ผู้เช่าต้องทำเหมือนเดิมคือจ่ายใหม่ ไม่คุ้มที่จะเพิ่มสถานะที่ห้า |
| ยืนยันการชำระ | เจ้าของหอกดอนุมัติ | สลิปปลอมและสลิปยอดไม่ตรงมีจริง |
| PDF | สร้างในแอปตอนกด ไม่เก็บไฟล์ | ไม่เปลืองพื้นที่ ไม่ต้องจัดการไฟล์เก่าตอนยกเลิกบิล |
| ปีในเลขที่บิล | ค.ศ. | ทุกหน้าในแอปแสดง ค.ศ. อยู่แล้ว การเปลี่ยนเป็น พ.ศ. ควรเป็นงานแยกที่ทำทั้งแอปพร้อมกัน |
| ข้อมูลเก่า | backfill ด้วย SQL | ผู้เช่าเห็นประวัติ 6 เดือนอยู่แล้ว ถ้าไม่ backfill ประวัติจะหายไปในวันมายเกรต |

## 1. ฐานข้อมูล

### ตาราง `invoices`

```sql
CREATE TABLE invoices (
  id                  BIGSERIAL PRIMARY KEY,
  invoice_no          TEXT NOT NULL,
  dorm_id             INT  NOT NULL REFERENCES dormitories(id) ON DELETE CASCADE,
  room_id             INT  NOT NULL REFERENCES rooms(id)       ON DELETE CASCADE,
  tenant_id           UUID REFERENCES tenant_profiles(id),
  billing_month       INT  NOT NULL CHECK (billing_month BETWEEN 1 AND 12),
  billing_year        INT  NOT NULL,

  room_price          NUMERIC NOT NULL DEFAULT 0,
  electricity_units   NUMERIC NOT NULL DEFAULT 0,
  electricity_cost    NUMERIC NOT NULL DEFAULT 0,
  water_cost          NUMERIC NOT NULL DEFAULT 0,
  cleaning_fee        NUMERIC NOT NULL DEFAULT 0,
  total               NUMERIC GENERATED ALWAYS AS
                        (room_price + electricity_cost + water_cost + cleaning_fee) STORED,

  status              TEXT NOT NULL DEFAULT 'unpaid'
                        CHECK (status IN ('unpaid','pending','paid','voided')),
  due_date            DATE NOT NULL,
  issued_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  issued_by           UUID NOT NULL,
  slip_url            TEXT,
  slip_submitted_at   TIMESTAMPTZ,
  rejection_reason    TEXT,
  paid_at             TIMESTAMPTZ,
  approved_by         UUID,

  voided_at           TIMESTAMPTZ,
  void_reason         TEXT,
  replaces_invoice_id BIGINT REFERENCES invoices(id),
  revision            INT NOT NULL DEFAULT 1,

  created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE UNIQUE INDEX invoices_one_active_per_period
  ON invoices (room_id, billing_year, billing_month) WHERE status <> 'voided';

-- เลขที่บิลไม่มีส่วนที่บอกหอ และเลขห้องซ้ำกันข้ามหอได้ ความไม่ซ้ำจึงผูกกับหอ
-- ไม่ใช่ทั้งตาราง — เลขที่เอกสารมีความหมายในขอบเขตของกิจการที่ออกมัน
CREATE UNIQUE INDEX invoices_no_per_dorm
  ON invoices (dorm_id, invoice_no);

CREATE INDEX invoices_room_period
  ON invoices (room_id, billing_year DESC, billing_month DESC);
CREATE INDEX invoices_dorm_period
  ON invoices (dorm_id, billing_year DESC, billing_month DESC);
```

**`total` เป็น generated column** เพื่อให้ยอดรวมคำนวณในฐานข้อมูล ไม่ใช่ในแอป
เป็นไปไม่ได้ที่ยอดในบิลจะไม่ตรงกับผลบวกของรายการ ไม่ว่าจะเขียนมาจาก client ตัวไหน

**unique index เป็น partial** เพื่อบังคับกฎ "หนึ่งห้อง หนึ่งงวด หนึ่งบิล" ที่ระดับฐานข้อมูล
ขณะที่ยังเก็บใบที่ยกเลิกไว้เป็นประวัติ การกดออกบิลซ้อนกันจะชนที่ constraint
ไม่ใช่สร้างบิลซ้ำเงียบๆ

**เก็บ `tenant_id` แยกจาก `rooms.current_tenant_id`** เพราะผู้เช่าย้ายออกได้
บิลค้างของคนเก่าต้องยังชี้ไปที่คนเก่า ไม่ใช่คนใหม่ที่เพิ่งย้ายเข้า

### เลขที่บิล

`INV-{YYYYMM}-{เลขห้อง}` เช่น `INV-202608-301`
ใบที่ออกใหม่แทนใบที่ยกเลิกต่อท้าย `-R{revision}` เช่น `INV-202608-301-R2`

**ความไม่ซ้ำผูกกับหอ ไม่ใช่ทั้งตาราง** — เลขที่บิลไม่มีส่วนที่บอกว่าเป็นหอไหน และ
`rooms.room_number` ซ้ำกันข้ามหอได้ ห้อง 301 ของสองหอในเดือนเดียวกันจึงได้สตริงเดียวกัน
ถ้าตั้ง `UNIQUE` ทั้งตาราง backfill ที่ห่อด้วย `BEGIN...COMMIT` จะล้มทั้งชุดเมื่อมีหอที่สอง
เลือกผูก unique กับ `(dorm_id, invoice_no)` แทนการยัดรหัสหอลงในเลขที่ เพราะเลขที่เอกสาร
มีความหมายในขอบเขตของกิจการที่ออกมัน และผู้เช่าไม่ควรต้องอ่านรหัสภายในระบบ

### วงจรสถานะ

```
                    ┌──────────────────────────────┐
                    │                              │ ปฏิเสธสลิป (+ เหตุผล)
                    ▼                              │
   [ออกบิล] ──▶ unpaid ──อัปสลิป──▶ pending ───────┤
                    │                              │
                    │                              └──อนุมัติ──▶ paid
                    │                                              │
                    └──────────── ยกเลิก (+ เหตุผล) ───────────────┘
                                        │
                                        ▼
                                      void ──▶ ออกใบใหม่ revision+1
```

การเปลี่ยนสถานะที่อนุญาต

| จาก | ไป | ใคร | ต้องมี |
|---|---|---|---|
| `unpaid` | `pending` | ผู้เช่า | `slip_url`, `slip_submitted_at` |
| `pending` | `paid` | เจ้าของหอ | `paid_at`, `approved_by` |
| `pending` | `unpaid` | เจ้าของหอ | `rejection_reason` |
| `unpaid` / `pending` / `paid` | `voided` | เจ้าของหอ | `voided_at`, `void_reason` |

ค่าใน `status` สะกดตรงกับ `InvoiceStatus.<ชื่อ>.name` ฝั่ง Dart ทุกตัวรวมทั้ง `voided`
จึงไม่ต้องมีตารางแปลงชื่อสถานะระหว่างสองฝั่ง ซึ่งเป็นจุดที่พลาดแล้วเงียบ

`voided` เป็นสถานะสุดท้าย ออกจากมันไม่ได้ การยกเลิกใบที่ `paid` ทำได้เพื่อรองรับกรณี
อนุมัติผิด และใบใหม่จะโยงกลับผ่าน `replaces_invoice_id` ทำให้สลิปที่จ่ายไปแล้วยังตามรอยได้

### RLS

ต่อยอดรูปแบบใน `database/rls_tenant_access.sql`

| ใคร | อ่าน | เขียน |
|---|---|---|
| เจ้าของหอ | บิลของหอตัวเอง | `INSERT` บิล · `UPDATE` สถานะทุกแบบ |
| ผู้เช่า | บิลที่ `tenant_id = auth.uid()` | ไม่มีสิทธิ์เขียนตรง — ส่งสลิปผ่าน RPC เท่านั้น |

ผู้เช่าไม่มี `UPDATE` policy เลย การส่งสลิปไปผ่านฟังก์ชัน `submit_payment_slip`
ที่เป็น `SECURITY DEFINER` ซึ่งตรวจเองว่าเป็นบิลของผู้เรียกและยังอยู่ในสถานะ `unpaid`
แล้วเขียนเฉพาะคอลัมน์สลิป

เลือกทางนี้เพราะ RLS policy จำกัดไม่ได้ว่า "คอลัมน์ไหนแก้ได้" — `WITH CHECK`
มองเห็นเฉพาะแถวใหม่ อ้าง `OLD` ไม่ได้ และ column-level `GRANT` ก็แยกไม่ออกเพราะ
เจ้าของหอกับผู้เช่าเป็น role `authenticated` เหมือนกัน ผลลัพธ์คือผู้เช่าแก้ยอดเงิน
หรือกดให้ตัวเองเป็น `paid` ไม่ได้ต่อให้เรียก API ตรง

### Storage

bucket ส่วนตัวใหม่ `payment-slip` แยกจาก `chat-image` เพราะสลิปคือหลักฐานการเงิน
อ่านผ่าน signed URL อายุ 1 ชั่วโมง ตามรูปแบบเดิมใน `supabase_service.dart:563`
path เป็น `{room_id}/{invoice_no}-{timestamp}.jpg`

### Backfill

`database/invoices_backfill.sql` สร้างบิลย้อนหลังจากมิเตอร์ที่มีอยู่ ใช้กฎเดียวกับ
`MockPaymentLedger.statusFor` คืองวดปัจจุบันเป็น `unpaid` งวดก่อนหน้าเป็น `paid`
เพื่อให้หน้าประวัติของผู้เช่าไม่เปลี่ยนหน้าตาในวันมายเกรต

รันครั้งเดียว มี `WHERE NOT EXISTS` กันการใส่ซ้ำ ตั้ง `issued_by` เป็นเจ้าของหอของหอนั้น
และ `revision = 1`

## 2. ชั้นโค้ดใน Flutter

### หลักการ

แยก **คำนวณ** ออกจาก **ดึงข้อมูล** ตรรกะบิลตอนนี้ฝังอยู่ใน `SupabaseService.fetchInvoices`
ซึ่งเรียก network ตั้งแต่บรรทัดแรก จึงเขียน unit test ไม่ได้ และนี่คือเหตุผลที่ `test/`
มี 7 ไฟล์แต่ไม่มีไฟล์ไหนทดสอบ billing ทั้งที่เป็นส่วนที่เกี่ยวกับเงิน

### โมเดล

| ชนิด | คืออะไร |
|---|---|
| `InvoiceDraft` | ร่างบิลที่คำนวณสดจากมิเตอร์ ยังไม่มีตัวตนในฐานข้อมูล |
| `Invoice` | ใบจริงที่ตรึงแล้ว มีเลขที่ มีสถานะ หนึ่งแถวในตาราง |

การแยกสองชนิดทำให้ compiler จับความผิดพลาดที่อันตรายที่สุดของฟีเจอร์นี้ให้ คือ
การเผลอเอาตัวเลขที่คำนวณสดไปแสดงหรือไปพิมพ์ลง PDF แทนตัวเลขที่ตรึงไว้

`Invoice` ถือ `dbId`, `invoiceNo`, `roomId`, `roomNumber`, `tenantId`, `tenantName`,
`billingMonth`, `billingYear`, ตัวเลขทั้งห้าช่อง, `status`, `dueDate`, `issuedAt`,
`slipUrl`, `slipSubmittedAt`, `rejectionReason`, `paidAt`, `revision`, `voidReason`

`InvoiceDraft` ถือ `roomId`, `roomNumber`, `tenantId`, `tenantName`, งวด, ตัวเลขทั้งสี่ช่อง
และ `SkipReason?` ที่บอกว่าทำไมออกบิลห้องนี้ไม่ได้

### เปลี่ยนแปลงใน `models.dart`

- `InvoiceStatus` เพิ่ม `voided`
- `MessageType` เพิ่ม `invoice` และ `ChatMessage` เพิ่ม `invoiceId`
  ตามรูปแบบเดิมของ `maintenanceRequestId`
- `PaymentChannel` ขยายเป็น `{bankName, accountNo, accountName, qrAssetPath}`
- **ลบ `TenantBill`** ตัวห่อนี้มีชีวิตอยู่เพื่อแปะสถานะจำลองบนบิลที่คำนวณสด
  เมื่อ `Invoice` มีสถานะจริงในตัวแล้วมันไม่เหลืออะไรให้ห่อ มีจุดเดียวที่แตะ
  `bill.invoice` คือ `tenant_bill_card.dart:23` ที่เหลืออีก 51 จุดเป็นแค่ชื่อชนิด

### ไฟล์ใหม่

**`lib/services/invoice_calculator.dart`** — Dart ล้วน ไม่ import supabase

`noMeterReading` ยังไม่จดมิเตอร์ · `alreadyIssued` ออกบิลงวดนี้ไปแล้ว
ผู้เรียกเป็นคนบอกว่ามีบิลอยู่แล้วหรือไม่ ตัวฟังก์ชันจึงไม่ต้องแตะฐานข้อมูล
ตรรกะการข้ามมีอยู่ที่เดียวและถูกทดสอบที่เดียว หน้าจอเอา `SkipReason` ไปแสดงตรงๆ

**`lib/services/invoice_lifecycle.dart`** — Dart ล้วนเช่นกัน

```dart
bool canTransition(InvoiceStatus from, InvoiceStatus to);
```

แยกจาก calculator เพราะเป็นคนละเรื่อง — ตัวหนึ่งตอบว่าบิลควรมียอดเท่าไร
อีกตัวตอบว่าบิลเปลี่ยนสถานะไปทางไหนได้ `InvoiceService` เรียกตรวจก่อนทุกครั้งที่จะ
`UPDATE` สถานะ เป็นด่านเดียวกับที่ RLS บังคับอยู่ฝั่งฐานข้อมูล

| `submitSlip()` | ผู้เช่าอัปสลิป |

### การ์ดบิลในแชท

เหตุการณ์ที่โพสต์เข้าแชทอัตโนมัติ

| เหตุการณ์ | รูปแบบ |
|---|---|
| ออกบิล | การ์ดสรุป งวด ยอดรวม ครบกำหนด ปุ่มเปิดบิล |
| ปฏิเสธสลิป | ข้อความ + เหตุผล |
| อนุมัติชำระ | ข้อความยืนยันรับเงิน |
| ยกเลิกบิล | ข้อความ + เหตุผล |

ทั้งสี่คือเรื่องที่ผู้เช่าต้องรู้และควรมีเป็นลายลักษณ์อักษร ไม่ใช่ตัวเลขที่เปลี่ยนเงียบๆ
ในอีกแท็บ เป็นเหตุผลเดียวกับที่คำขอซ่อมโพสต์เข้าแชทอยู่แล้ว

การ์ดแสดง **สถานะสด ไม่ใช่สถานะตอนส่ง** โดย `ChatViewModel` ดึงบิลของห้องนี้หนึ่งครั้ง
ตอนเปิดแชทแล้ว resolve ตาม `invoiceId` เหมือนที่ `_resolveAttachmentUrls`
(`supabase_service.dart:551`) ทำกับรูปแบบ batch อยู่แล้ว เพิ่ม query เดียวต่อการเปิดแชท
หนึ่งครั้ง แลกกับการไม่มีการ์ดค้างที่บอกว่า "ค้างชำระ ฿5,240" ทั้งที่จ่ายไปแล้วเมื่อวาน

กดการ์ดแล้วผู้เช่าเปิดแผ่นชำระเงิน เจ้าของหอเปิดแผ่นรายละเอียดบิล
ทั้งสองฝั่งเรียก widget เดียวกันที่ส่ง action คนละชุดเข้าไป

## 4. PDF

Dependency ใหม่ `pdf` และ `printing`

**ฟอนต์คือจุดที่พังเงียบที่สุด** `pdf` ใช้ Helvetica ที่ไม่มี glyph ภาษาไทย
ถ้าไม่ฝังฟอนต์เอง บิลจะออกมาเป็นกล่องว่างทั้งใบโดยไม่มีอะไรเตือนตอน compile
ต้องเพิ่ม `Sarabun-Regular.ttf` และ `Sarabun-Bold.ttf` ลง `lib/assets/fonts/`
แล้วประกาศใน `pubspec.yaml`

เอกสารเป็น A5 แนวตั้ง พอดีกับการเปิดดูบนมือถือ

```

│  ออกเมื่อ 1 กันยายน 2026              │
│  ─────────────────────────────────── │
│  ค่าห้อง                     3,500.00│
│  ค่าไฟ  142 หน่วย × 8.00     1,136.00│
│  ค่าน้ำ                        404.00│
│  ค่าทำความสะอาด                200.00│
│  ─────────────────────────────────── │

│  ครบกำหนดชำระ  5 กันยายน 2026        │
```

## 5. การจัดการข้อผิดพลาด

| สถานการณ์ | จัดการอย่างไร |
|---|---|
| ออกบิล 12 ห้องล้มกลางคัน | `insert` แถวทั้งหมดใน statement เดียว Postgres รับประกัน all-or-nothing ให้เอง ไม่มีสภาพออกไป 7 ห้องแล้วค้าง |
| โพสต์แชทล้มหลังบิลออกแล้ว | ข้อความก็เป็น batch insert เดียว ถ้าล้มจะรายงานว่าออกบิลสำเร็จแต่แจ้งเตือนไม่สำเร็จ พร้อมปุ่มส่งซ้ำที่ข้ามใบที่มีข้อความแล้ว **ไม่ rollback บิล** เพราะบิลคือของจริง ข้อความคือการแจ้งเตือน |
| กดออกบิลรัวสองครั้ง หรือเจ้าของหอสองเครื่อง | ชนที่ partial unique index ได้ `23505` แปลงเป็น "บางห้องถูกออกบิลงวดนี้ไปแล้ว กรุณาโหลดใหม่" |
| อัปสลิปสำเร็จแต่อัปเดตแถวล้ม | อัปโหลดก่อนแล้วค่อยอัปเดต ถ้าอัปเดตล้มจะลบไฟล์ที่เพิ่งอัปทิ้งแบบ best-effort ไม่ให้เหลือไฟล์ที่ไม่มีใครอ้างถึง |
| signed URL ของสลิปหมดอายุ | สร้างใหม่ทุกครั้งที่เปิดแผ่นตรวจสลิป ไม่ cache ข้าม session |
| โหลดสถานะบิลในแชทล้ม | การ์ดยังแสดงงวดและยอดตามปกติ แค่ไม่มีป้ายสถานะ แชทต้องไม่พังเพราะบิลโหลดไม่ได้ ใช้ `SectionErrorNote` ตามรูปแบบเดิม |
| RLS ปฏิเสธ | ผ่าน `formatErrorMessage` ที่มีอยู่แล้ว |
